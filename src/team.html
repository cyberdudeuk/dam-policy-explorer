Process returns and answer questions

For the GDS Government Data directorate - Data Quality & Management team: how a return travels from the mailbox to the register, and how to give clear, consistent answers.

This page describes how our team works and the processing we propose. It is not published guidance.

What do you need to do?

  • A return has arrived: check it
  • Someone has asked a question: answer it
  • See every step of the process
  • See what still needs deciding

How does a return move through the team?

Proposed design, not yet built The same process at four levels of detail, from a summary to every decision. Start with the summary and go deeper only if you need to.

From returns to action, in five stages

  1. Collect

    Organisations send their returns. We keep each original file exactly as it arrived.

  2. Assure

    We check every return. Where something needs correcting, we ask the organisation to correct it.

  3. Consolidate

    Accepted returns go into one cross-government register of critical data assets.

  4. Understand

    Quick measures first, then a fuller dashboard, show where things stand.

  5. Act

    We use what we learn to decide where support is needed most.

Evidence we can trust

The original return, every correction, every checking result and every decision is kept and can be traced.

One register

The register is the bridge between the returns we receive and the analysis across government.

Insight we can act on

We can see where ownership, stewardship, catalogues, quality plans and sharing need support.

Text version of the map
  1. P01 Fill in the Baseline Return (Organisation sending the return). The organisation fills in the Baseline Return workbook (version 3). The Baseline Return is the first list of critical data assets each organisation sends. Next: Send the return.
  2. P02 Send the return (Organisation sending the return). The organisation emails the finished workbook to the team’s shared mailbox. Next: Email and workbook arrive.
  3. P03 Email and workbook arrive (Team mailbox). The email and its attached workbook (an XLSX file) arrive in the shared mailbox. Next: Give it a reference number.
  4. P04 Give it a reference number (Receiving and logging). Each return gets its own submission reference, with the sender, the time it arrived and the email’s ID. Next: Keep the original.
  5. P05 Keep the original (Receiving and logging). The original file is saved exactly as it arrived. Nobody changes it. Next: Restricted library.
  6. DS01 Restricted library (Safe storage). Originals are kept in a restricted SharePoint library (Microsoft’s shared document store). Next: Record the details.
  7. P06 Record the details (Receiving and logging). The return’s details are recorded and its status is set to “received”. Next: Check the workbook.
  8. SP01 Check the workbook (Checking). Checks that the file opens, is the approved version 3 and has the expected layout. Next: Is the workbook valid?.
  9. D01 Is the workbook valid? (Checking). Is this the approved version 3 workbook, laid out as expected? Next: Check each asset (if yes); Log the issue (if no).
  10. SP02 Check each asset (Checking). Checks every asset in the return: required details, allowed answers, purposes and links between answers. Next: Anything blocking or unclear?.
  11. D02 Anything blocking or unclear? (Checking). Is there a mistake, or something unclear, that stops us using the return? Next: Log the issue (if yes); Accept the return (if no).
  12. P07 Log the issue (Review and questions). The issue is written in the checking log, so nothing is lost. Next: A person reviews it.
  13. P08 A person reviews it (Review and questions). A team member looks at the issue and decides what to do. Next: Does it need correcting?.
  14. D03 Does it need correcting? (Review and questions). Does the organisation need to change something, or can we accept it as it is? Next: Ask for a correction (if yes); Accept the return (if no).
  15. P09 Ask for a correction (Review and questions). We email the coordinator to ask for a correction. They send a corrected return, which starts again at the mailbox. Next: Email and workbook arrive (if corrected return).
  16. P10 Accept the return (Review and questions). The return is accepted. We keep the original, the checked version, the checking log and our decision. Next: Add to the register.
  17. SP03 Add to the register (The register). Each accepted asset is added to the register, or updates its earlier entry, keeping a record of where it came from. Next: The register.
  18. DS02 The register (The register). One managed register of critical data assets across government. Every entry shows where it came from. Next: Work out quick measures; Update the dashboard.
  19. SP04 Work out quick measures (Measures and action). Quick measures from the register, available straight away. Next: Quick measures.
  20. SP05 Update the dashboard (Measures and action). Updates the fuller analysis behind the dashboard. Next: Dashboard.
  21. O01 Quick measures (Measures and action). For example: how many assets, and how many have an owner, a steward and a quality plan. Next: Decide where to help.
  22. O02 Dashboard (Measures and action). Views for senior leaders and for each department. Next: Decide where to help.
  23. P11 Decide where to help (Measures and action). Find where the policy is not yet met, who needs most support and what patterns there are across government. Next: the end.
What the register holds

One entry for each asset, as each organisation reported it:

  • Organisation
  • Lasting asset reference
  • Submission reference
  • Return version
  • Reporting cycle
  • The 24 details from the version 3 workbook
  • The original file
  • Checking result
  • Review decision
  • Where each value came from

Each value can be traced from what was sent, to what was checked, to what we accepted.

The seven jobs, step by step

Each job is a step on the map, opened up. The design notes call these workflows. and are the proposed tools.

WF01 · Receiving and logging

Receive the return

: Outlook shared mailbox and Power Automate

  1. An email arrives in the shared mailbox
  2. Is it a data asset return?
  3. Is a workbook (XLSX file) attached?
  4. Record the email’s ID, the sender and the time it arrived
  5. Give the return a submission reference

Result: A submission record

WF02 · Safe storage

Keep the original and record it

: Power Automate and a restricted SharePoint library

  1. Save the original file exactly as it arrived
  2. Store it in the restricted library
  3. Record its details
  4. Set its status to “received”

Result: The original, kept safe, and its record

WF03 · Checking

Check the workbook

: Power Automate and Office Scripts

  1. Does the file open?
  2. Is it the approved version 3 workbook?
  3. Is the layout as expected?
  4. Are all the required columns there?
  5. Has the worked example been removed?
  6. Has anything else in the layout been changed?

Result: Pass, or an issue for the team to review

WF04 · Checking

Check each asset

: Power Automate and Office Scripts

  1. For each asset in the return
  2. Are the required details filled in?
  3. Are the answers from the allowed lists?
  4. Check the answers on the seven critical purposes
  5. Do linked answers agree with each other?
  6. Is the asset’s identity clear?
  7. Record its position on owner, steward, catalogue, being findable, quality plan, sharing, classification, origin and location data

Result: For each asset: pass, policy gap or error

WF05 · The register

Add to the register

: The register workbook

  1. Take the accepted assets from the return
  2. Match the organisation to its register reference
  3. Match each asset to its lasting asset reference
  4. Is it new? Add it. Is this a new return or version? Update it
  5. Keep the record of its source, its checks and our decision

Result: An up-to-date register entry for each asset

WF06 · Measures and action

Work out quick measures

: Excel

  1. Number of critical data assets
  2. Share with a data quality plan or equivalent
  3. Share with an owner
  4. Share with a steward
  5. Share in a data catalogue
  6. Share that can be found by others
  7. Sharing between organisations
  8. Purposes served
  9. Where each return has got to

Result: Quick measures, before the full dashboard is needed

WF07 · Measures and action

Update the dashboard

: The analytics dashboard for the Data Asset Management (DAM) Policy

  1. Senior leaders’ view: overall standards, purposes, sharing and how many organisations have replied
  2. Department view: quality plans, sharing, assets by purpose, gaps against the standards and priorities

Result: A view of where things stand, to decide where to help

The five decisions, and where each answer leads

D01

Is the workbook valid?

Is this the approved version 3 workbook, laid out as expected?

  • YesGo on to check each asset (WF04)
  • NoLog the issue and pass it to a person to review

D02

Is anything blocking or unclear?

After checking each asset: is there a mistake, or something unclear, that stops us using the return?

  • NoAccept the return
  • YesLog the issue and pass it to a person to review

D03

Does it need correcting?

Having looked at the issue: does the organisation need to change something?

  • NoAccept the return as it is
  • YesEmail the coordinator to ask for a correction. The corrected return starts again at the mailbox

R04

Pass, policy gap or error? (each asset)

What did checking this asset find?

  • PassIt meets the checks. It goes into the register.
  • Policy gapAn honest answer that shows the policy is not yet met, such as “no quality plan yet”. It goes into the register and shows up in the measures, so we can offer support. It is not an error.
  • ErrorA mistake or something unclear. It goes to a person to review and may need a correction.

A policy gap moves forward. Only an error goes sideways for correction.

R05

New entry or update? (adding to the register)

Is this asset already in the register?

  • No, it is a new assetAdd it as a new entry
  • Yes, and this is a new return or versionUpdate the entry, keeping the record of its source, its checks and our decision

How do I answer a question?

Every answer follows the same seven steps, so organisations get the same answer whoever they ask.

  1. Answer first. Start with the answer, in one or two sentences, using the words the person used.
  2. Say where it comes from. Name the document and the part of it. If two documents disagree, the policy comes first, then the guidance on identifying and recording assets, then the other guidance, then our own playbooks.
  3. Say how sure we are. Use one of the five labels below. Never present a suggestion as if it were agreed.
  4. Give the other reading. If the text could mean something else, say so, and say why we chose this reading.
  5. Say what to note down. Tell them what to record in their return about the reading they used, so their return can be checked against our answer.
  6. Get a second check. If the answer is anything other than published guidance or an agreed decision, a second team member checks it before it is sent.
  7. Publish it. Add the answer, reworded so no person or organisation can be identified, to our published answers. The question is only finished when the answer is published.

How sure is the answer?

Published guidance
The policy or the guidance says this.
Agreed decision
A named person decided this, on a known date.
Our suggested reading
Our best reading of unclear text. Not agreed yet.
Working definition
A meaning we use for now, until there is an agreed one.
Not decided
Nobody can answer this yet. Say who will decide.

The full path of a question, from arriving to published
  1. Log every question once, however it arrived, with who asked, their organisation, the topic and the date.
  2. Sort it by topic, and look for an answer we have already given before writing a new one.
  3. Answer from the documents, in order: the policy, the identifying guidance, the other guidance, then our playbooks.
  4. Where the documents say nothing or disagree, write a suggested reading, mark it as suggested, and write down the case against it.
  5. Get a second check from another team member.
  6. If the answer affects other organisations, send it to the person who owns the decision. Tell the person asking that we are waiting for a decision.
  7. Reply, following the answer standard.
  8. Publish the answer where people will find it.
  9. When guidance changes, reopen every answer that relied on the part that changed.



How do I check a return?


Check a return, then write one message to the organisation: what must change, what we need to ask, and the policy gaps we have recorded.


The file check needs JavaScript, which is switched off or blocked in your browser. You can still use the list of checks below to go through your file by hand.



  
  
  
  
  

  
Files are read by your own browser. Nothing is uploaded or sent anywhere.

  

  




What the check looks for
Must fix
  • The file has all 24 columns of the version 3 template.
  • The 13 details that must be filled in are filled in.
  • Text fits the length the template allows.
  • Yes or No questions say Yes or No.
  • The security marking is OFFICIAL or OFFICIAL-SENSITIVE. SECRET and TOP SECRET data does not go in.
  • Critical purposes are numbers from 1 to 7, each used once.
  • Answers chosen from a list use one of the list’s values, where we have the list.
  • An asset recorded “In catalogue” gives its catalogue reference.
  • Geospatial standards come from the list, and “Not applicable” stands alone.
  • No asset is marked “Out of scope”.
  • There are no email addresses, in the return or in your list of assets left out. The return does not record people’s names or contact details.
  • The template’s worked example has been deleted.
  • No quote mark is left open, which would join rows together.
We will ask
  • An identifier used more than once, written in any mix of capitals. This is allowed only for an approved version or licence variant.
  • In your list of assets left out (our suggestion): which test each one failed, and why.
Policy gap These are accepted. They are not mistakes: they show us where to help.
  • No data owner or no data steward assigned yet.
  • The asset is not in a data catalogue yet.
  • A gap in data quality assurance.
Tips
  • Recommended details are filled in: sharing status, version and discoverability.
  • The security marking is written exactly as OFFICIAL or OFFICIAL-SENSITIVE.
  • Asset names spell out abbreviations, and no two assets have almost the same name.
What the check cannot do: it cannot tell whether a detail marked “Fill in if it applies” applies to your asset. For sharing status, access rights, licence, quality status and discoverability, it checks that you answered, but not your answer, because we do not yet have the workbook’s full lists.



All 11 steps for processing a return by hand
  1. Log it and say thank you. Record the file, who sent it, their organisation and the date, and give it a reference number. Reply to say it has arrived. Keep the original file unchanged.
  2. Check who sent it. Match it to the organisation and its group. Note if the organisation has changed its name or merged.
  3. Check the file. Use the file check above. It finds missing columns, wrong values and anything above OFFICIAL-SENSITIVE.
  4. Check each asset. Look at the security marking and the critical purposes, whether an owner and a steward are assigned, the quality plan status and the plain-English names.
  5. Compare with what we already know. Compare the return with the starter list we made for the organisation. Note anything on our list that is missing from the return.
  6. Look for assets that should be there. Other organisations may say they get data from this one. If that data is not in the return, ask about it. Leaving an asset out avoids work, so it can happen without anyone meaning to.
  7. Ask once. Send one email with all the questions, clear enough to be answered in one reply. The file check above writes it for you.
  8. Accept it. Accept the return and mark its assets as confirmed by the organisation.
  9. Check the group is complete. For each department, check every organisation in its group has sent a return or is recorded as left out.
  10. Add up the figures. Work out how many organisations have sent a return, and how complete the returns are. Only report a middle value (median) for a type of organisation when three or more of them answered.
  11. Pass on what we learned. Turn repeated questions into published answers, and fix the template where it confused people.



What do we keep a record of?


Log every question and every return, so nothing is lost and we can see how quickly we respond.


 Download the question log template (CSV)  Download the return log template (CSV)


What to record, and why


For each question: the date it arrived, how it arrived, who asked and their organisation, the topic, the answer, how sure we are, who checked it, the date we replied and the date we published it.


For each return: the date it arrived, the organisation, the file name, what the check found, the questions we sent and when, and the date we accepted it.


These let us measure how long people wait for a reply and how many rounds of questions a return needs.

      How this site was made, and what it does with your files
      

        
Your files stay with you. When you check a file, it is read by your own browser. Nothing is uploaded, stored or sent anywhere. There are no cookies and no tracking.

        
Where the content comes from. Facts about the policy come from the published Data Asset Management Policy and its guidance on GOV.UK. How the team processes returns is the team’s own proposed design, and the page says so. The full list of sources is in our sources list.

        
How it was made. Made for the GDS Government Data directorate - Data Quality & Management team with the help of an AI assistant (Claude, made by Anthropic), which also drew the icons. Facts about the policy and its guidance were checked against the published pages on GOV.UK. The team is responsible for the content. Content last checked: 13 November 2026.

        
No guarantee. This is a prototype. If anything here disagrees with the published guidance on GOV.UK, the guidance is right. Please tell us so we can fix it.

        
Contact. We use a contact form so that messages reach whoever is on duty. The form is on GitHub and what you write there can be seen by others, so do not include personal or sensitive information.
